# تقرير تحسين الأداء وفصل مصادر البيانات

التاريخ: 2026-10-06. أساس العمل: `ceedc241d993d5f0ee273e8e3de591cf256bc728`.
الفرع: `improve/performance-laserfiche-routing`.

الحالة: تغييرات البنية الداخلية مكتملة ومختبرة آليًا، لكن قبولها النهائي على مستودع Windows الفعلي لم يُنفذ. هذه البيئة لا تحتوي على Laserfiche أو قاعدة OCR أو النموذج المحلي الخاص بالمستخدم. لا يُعد هذا التقرير شهادة بأن جميع اختبارات القبول الفعلية نجحت.

## A. سبب البطء

- مهلة 900 ثانية كانت معرفة في `Program.cs` لعميل `ReportsGraph`، أي الانتظار لاتصال خدمة الإجابة، وليست قياسًا لمدة بحث Laserfiche.
- خدمة الإجابة كانت تنفذ استخراجًا ثم صياغة ثم مراجعة: 3 استدعاءات للنموذج، أو 4 عند إعادة محاولة الاستخراج. لم يكن عميل Ollama في Python يحدد مهلة واضحة لكل استدعاء.
- `LiveRepositoryReportService` كان يجتاز جميع المجلدات، ثم يجلب تفاصيل كل وثيقة، ثم حقول كل وثيقة، ويطبق شرط الحقل في C#. مثال 73 وثيقة ينتج 146 طلبًا إضافيًا للتفاصيل والحقول، غير طلبات المجلدات والجذر.
- جميع طلبات `/api` لنفس الجلسة كانت تمسك القفل طوال تنفيذها. لذلك سؤال بطيء كان يؤخر التنقل وقراءة الحالة وتبديل المستودع.
- الأسئلة التي لم يتعرف عليها مسار الحصر كانت تتجه إلى embeddings ثم قاعدة المقاطع ثم التحقق من وثائق المرشحين ثم النموذج. وكانت مقاطع metadata القديمة قابلة للدخول ضمن البحث عن المحتوى.
- معالج تسجيل HTTP كان يقرأ أجسام استجابات Laserfiche النصية ويسجلها. أزيل هذا التحميل والتسجيل.

لم تتوفر سجلات طلب الـ900 ثانية الأصلي أو جهاز المستخدم. لذلك لم يُنسب زمن فعلي لكل مكوّن على جهازه، ولم يُفترض أن النموذج وحده استهلك 900 ثانية. الأسباب أعلاه مثبتة من مسار الكود، والقياسات الجديدة تحدد سبب أي طلب لاحق.

## B. البنية الحالية

| المسار | مصدر البيانات | التنفيذ |
| --- | --- | --- |
| LASERFICHE_QUERY | Laserfiche الحالي | أدوات بحث وحقول وقوالب وتفاصيل، ثم تقرير Backend |
| OCR_QUERY | النص المستخرج في جدول documents الحالي | استرجاع النص، التحقق من صلاحية الوثائق ووجودها الحالي، ثم AI |
| HYBRID_QUERY | Laserfiche ثم نصوص الوثائق المطابقة | بحث مباشر، IDs الحالية، OCR لهذه IDs داخل المستودع نفسه، ثم AI |

`QuestionRouter` يستخدم قواعد للأسئلة الواضحة؛ الأسئلة الأخرى تستخدم استدعاء توجيه واحدًا مقيدًا بمخطط JSON. النموذج يرسل عملية وحقلًا وقيمة، ولا يرسل HTTP أو SQL أو تعبير بحث. Backend يتحقق من الحقول والقوالب والأرقام والتواريخ والحدود والترتيب ويبني التعبير.

الأسماء والمسارات التي تظهر مع أدلة OCR تُستبدل بالقيم الحالية من Laserfiche. لا يُستعمل الاسم القديم أو الحقل المخزن في قاعدة النصوص كحقيقة حالية. المقاطع القديمة من نوع `laserfiche-metadata` مستبعدة، والصفوف القديمة باقية؛ لم تُنفذ عملية تنظيف أو حذف أو migration.

حُفظت وظيفة الفهرسة اليدوية ومحرك OCR وإعداداته. تغيير الحفظ فقط: الفهرسة الجديدة تحفظ نص الصفحات والمقاطع ومعلومات مصدر النص ومفتاح RepositoryId + EntryId. لا تنشئ embeddings لحقول المستودع ولا تحفظ نسخة من أسماء الوثائق والمسارات والقوالب وقيم الحقول. بصمة المصدر تستخدم للتحقق من إمكانية إعادة استخدام النص الموجود. بقي اسم `document-metadata` لسجل تتبع استخراج النص للتوافق مع الجدول الحالي، دون نسخة بيانات المستودع داخله.

لا يوجد مسح عند بدء التشغيل أو داخل مسار سؤال metadata. تقارير التجميع وHybrid تتبع صفحات نتيجة بحث واحدة عند حاجتها لجميع المطابقات، دون اجتياز شجرة المجلدات. حدها 10,000 نتيجة و45 ثانية للعملية؛ إذا لم تكتمل، تفشل بوضوح بدل إعلان حصر ناقص. لا ترسل مجموعة البيانات الكاملة إلى النموذج.

## C. صحة النتائج

- العدد يعتمد على `@odata.count`/العدد الكامل في الاستجابة، وليس حجم الصفحة. اختبار 20 صفًا مع إجمالي 73 أعاد 73.
- عندما يغيب العدد ويوجد استمرار، لا يختلق Backend عددًا. `IsTotalCountExact=false` يمنع عرضه كإجمالي مؤكد.
- الصفحة الثانية تحتفظ برقمها ولا تعيد إسقاط الصفوف التي أسقطها `$skip` بالفعل.
- الاسترجاع الكامل لا يضع `$top` كحد نهائي للمجموعة. يتبع nextLink مرة واحدة لكل صفحة، ويرفض الدوران أو المضيف المختلف أو عدم تطابق الصفوف مع العدد الكامل.
- صححت صيغة بحث الحقل إلى `{[]:[إجراء الوثيقة]="تحت الإجراء"}`، وصيغة القالب إلى `{[اسم القالب]:[]}`. تُجلب تعريفات الحقول والقوالب من المستودع الحالي قبل بناء الطلب.
- أسماء الحقول العربية تطابق التعريف الحقيقي مع تحمل الهمزات والمسافات في اسم الحقل؛ قيمة الحقل تظل قيمة البحث المطلوبة. مطابقة اختلاف الهمزة في قيم البيانات يجب اختبارها في المستودع الحقيقي.
- الحساب والتجميع والترتيب والنسبة في Backend. الحقول متعددة القيم ذات `hasMoreValues` لا تنتج تجميعًا ناقصًا.
- نتيجة الصفحة الجزئية لا توصف بأنها جميع الوثائق. نتائج OCR مقاطع مختارة، وقد لا تمثل كل صفحات الوثيقة أو كل المطابقات؛ يظهر ذلك في نطاق الإجابة.
- أسماء حالات مثل «المكتملة» لا تُحوَّل افتراضيًا إلى قيمة مخترعة مثل «مكتمل» أو «قبول». يطلب التطبيق قيمة الحقل المسجلة؛ يمكن السؤال «إجراء الوثيقة يساوي [القيمة الحقيقية]».

هذه أزمنة fixture محلي وليست أزمنة جهاز Windows أو مستودعه الفعلي. مدة توليد النموذج الفعلي ومدة قاعدة OCR الفعلية غير مقاستين. لا توجد نسبة تحسن مفترضة.

السجلات الجديدة تتضمن RequestId ونوع السؤال والمستودع والأداة والمدد والحالة: ROUTER وLASERFICHE وLASERFICHE_HTTP وEMBEDDING وSUPABASE وAI وTOTAL. لا تسجل أجسام استجابات HTTP أو نص OCR أو كلمات المرور أو التوكنات. لا توجد صفحة مراقبة جديدة.

## E. الاستقرار

- الموقع يبدأ دون AI أو Supabase، ولا يبدأ فهرسة أو OCR تلقائيًا.
- أسئلة Laserfiche المعروفة لا تستدعي قاعدة النصوص أو embeddings أو خدمة الإجابة.
- OCR/Hybrid عند انقطاع قاعدة النصوص: «محتوى الوثيقة غير متاح حاليًا».
- انقطاع AI: خطأ عربي مضبوط؛ سؤال بسيط معروف مثل العدد يستمر دون AI.
- انقطاع Laserfiche: يفشل السؤال بدل عدد مخزن أو إجابة متخيلة.
- طلب متجاوز المهلة: رسالة عربية موحدة. لا يُعرض نص exception أو StackTrace في أخطاء المحادثة.
- مهلة سؤال كاملة 180 ثانية، ومهلة عملية بحث Laserfiche 45 ثانية، ومهلة اتصالاته HTTP بحد أعلى 45 ثانية. فحوص الحالة محدودة بـ10 ثوانٍ.
- PostgreSQL: اتصال 10 ثوانٍ وأمر افتراضي 20 ثانية، واستعلام المحتوى بحد أقصى 30 ثانية. قراءة توفر المقاطع في القائمة محدودة بـ5 ثوانٍ ولا تمنع عرض قائمة Laserfiche عند الفشل.
- Python يسمح بتوليد واحد في الوقت نفسه ويرفض الطلب الزائد سريعًا بـ429؛ لا ينشئ طابور توليد طويلًا.
- CancellationToken ينتقل إلى dependencies، دون زر إلغاء جديد. قد يستمر استدعاء Ollama الذي بدأ بالفعل حتى مهلته؛ لا توجد آلية إلغاء توليد على مستوى النموذج نفسه.

## H. التشغيل والقبول المتبقي

تم تشغيل Web فعلًا، ونجحت الصفحة وحالة الجلسة مع غياب الخدمات. نجح تسجيل الدخول وسؤال العدد والحقل والقوالب عبر HTTP مع Laserfiche تجريبي. اختُبرت أخطاء توقف قاعدة النصوص وLaserfiche، ومسار Hybrid اختير قبل فشل النص.

لم تُختبر قراءة OCR ناجحة من قاعدة المستخدم ولا إجابة ناجحة من نموذجه الفعلي. اختبارات الإجابة الآلية تستخدم نموذجًا تجريبيًا؛ لا تعادل قياس جودة النموذج الحقيقي. تعذر تشغيل Chromium في هذه البيئة بسبب فشل تنزيله، لذلك لا يوجد ادعاء بأن Browser Console الخاص بالتطبيق الحي نظيف. اختبارات DOM والتنزيل نجحت، وملفات الواجهة لم تتغير.

قبل الدمج والاعتماد على Windows:

1. أوقف عملية Web القديمة، وشغل clean/restore/build/test ثم Web بالطرق الحالية. أعد تشغيل خدمة `tools/reports-graph` أيضًا؛ تغييرات Python لا تدخل في `dotnet build`.
2. قارن العدد وشرط «إجراء الوثيقة» وقيمته مع Laserfiche لنفس حساب المستخدم والمستودع. جرّب البحث بقيمة الحقل المكتوبة فعلًا، بما فيها الهمزة.
3. اختبر أسماء القوالب والMetadata وأحدث 10 وثائق وتاريخ اليوم. تحقق من قبول صيغة تاريخ ISO في إعدادات API/السيرفر المحلي؛ تاريخ «اليوم» يستخدم `now`.
4. أضف وثيقة اختبار، غيّر اسمها وحقلها ثم احذف وثيقة الاختبار فقط، وأعد السؤال بعد كل خطوة. يجب أن تظهر التغييرات دون فهرسة.
5. اسأل عن محتوى 618، ثم لخصها، ثم لخص محتوى الوثائق المطابقة لشرط الحقل. راجع نطاق المقاطع والأسماء الحالية؛ لا تفترض تلخيص جميع الصفحات إذا كان النطاق جزئيًا.
6. أوقف كل dependency منفردًا وتحقق من الرسالة العربية واستمرار باقي وظائف الواجهة.
7. افحص Console/Network للطلبات المكررة والمعلقة والأخطاء غير المتوقعة. راجع سجلات المدد الفعلية لتحديد السرعة على جهازك.

معيار النهاية الكامل يتطلب هذه المقارنة الفعلية؛ الفرع جاهز للمراجعة والتجربة، وليس مثبت القبول النهائي على بيئة العمل بعد.
